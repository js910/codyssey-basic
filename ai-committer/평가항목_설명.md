# AI Committer 평가 항목 설명

이 문서는 AI Committer 프로젝트를 시연하고 설명할 때 필요한 실행 흐름, 평가 항목별 답변, 구현상의 한계와 개선 방향을 정리합니다.

## 프로젝트 한 줄 소개

AI Committer는 Git 변경 사항을 Gemini API에 전달해 커밋 메시지 또는 Pull Request 초안을 생성하는 CLI 도구입니다. 생성 결과는 초안으로 출력하고, 커밋이나 PR을 자동으로 게시하지 않습니다.

## 실행 흐름

1. `main.py`가 `commit` 또는 `pr` 명령과 CLI 옵션을 읽습니다.
2. `git_utils.py`가 `git status --short`와 `git diff`로 변경 사항을 수집합니다.
3. 변경 사항이 없으면 안내 메시지를 출력하고 API 호출을 건너뜁니다.
4. `--safe-mode`를 지정한 경우 diff의 일부 민감정보를 마스킹하고 길이를 제한합니다.
5. `prompts.py`가 작업에 맞는 프롬프트를 구성합니다.
6. `gemini.py`가 API 키를 확인하고 Gemini API를 호출합니다.
7. `validator.py`가 생성 결과의 형식을 검사하고, `main.py`가 결과를 출력합니다.

## 파일별 역할

| 파일 | 역할 |
|---|---|
| `main.py` | CLI 옵션 처리, 실행 흐름 제어, 결과 출력 |
| `git_utils.py` | Git 명령 실행, 민감정보 마스킹, diff 길이 제한 |
| `prompts.py` | 커밋·PR 생성을 위한 프롬프트 구성 |
| `gemini.py` | API 키 확인 및 Gemini API 요청 |
| `validator.py` | 커밋 제목과 PR 형식 검증 |

## 시연 명령

```bash
python main.py commit
python main.py pr
python main.py commit --temperature 0.8
python main.py commit --max-tokens 200
python main.py commit --safe-mode
```

실행 전에 `GEMINI_API_KEY` 환경변수가 설정되어 있어야 합니다.

## 항목 1. 기능 시연 및 결과 확인

### 1-1. 프로젝트 루트에서 커밋 메시지가 출력되는가?

`python main.py commit`을 실행하면 status와 diff를 모아 Gemini에 전달하고, 응답을 `Commit Message` 아래 출력합니다. 첫 번째 비어 있지 않은 줄을 제목으로 간주해 72자 제한을 검사합니다.

### 1-2. PR 제목과 본문 초안이 출력되는가?

`python main.py pr`은 현재 브랜치와 변경 내용을 포함해 프롬프트를 만들고, 응답에서 `PR 제목:`과 `PR 본문:`을 추출합니다. 제목과 본문을 구분해 터미널에 출력합니다.

### 1-3. API 키가 없으면 오류를 출력하고 종료하는가?

`gemini.py`의 `create_client()`가 `GEMINI_API_KEY`를 확인합니다. 설정되지 않았다면 `RuntimeError`를 발생시키고, `main.py`가 `[ERROR]` 메시지를 출력합니다. 현재 구현은 오류 출력 후 프로세스 종료 코드가 0일 수 있습니다. 자동화에서 정확히 감지하도록 개선할 때는 실패 종료 코드를 설정해야 합니다.

### 1-4. 변경이 없으면 안내 메시지를 출력하는가?

`collect_changes()`에서 status와 diff가 모두 비어 있으면 `[INFO] 변경 사항이 없습니다.`를 출력하고 API 호출을 하지 않습니다.

### 1-5. Why / What / How to Test 및 불릿을 포함하는가?

PR 프롬프트에서 `## Why`, `## What`, `## How to Test`와 각 섹션의 불릿을 요구합니다. 생성 후 `validate_pr()`가 섹션 존재 여부와 섹션별 불릿 존재 여부를 확인합니다. 모델 응답은 항상 규칙을 지키는 것이 아니므로 프롬프트와 코드 검증을 함께 사용합니다.

### 1-6. temperature 또는 max-tokens를 바꾸면 차이가 재현되는가?

두 옵션 모두 CLI에서 설정해 API 요청에 전달할 수 있습니다. temperature는 생성 결과의 변동성에 영향을 주고, max tokens는 응답 길이를 제한합니다. 모델의 생성은 확률적이므로 특정 문구 차이가 매번 똑같이 재현된다고 보장하지 않습니다. 옵션이 요청에 반영되고 결과의 경향에 영향을 준다고 설명하는 것이 정확합니다.

### 1-7. 제목 길이 및 형식 규칙을 만족하는가?

프롬프트는 커밋 제목을 72자 이내, PR 제목을 80자 이내로 요청합니다. 검증 코드도 이 길이 제한을 확인합니다. Conventional Commits 형식은 프롬프트에서 요구하지만, 현재 코드가 `feat:` 등의 형식 자체를 별도로 강제 검증하지는 않습니다.

## 항목 2. 설계와 구현 이유

### 2-1. Git 변경 수집과 API 호출을 왜 분리했는가?

Git 명령 실행은 로컬 저장소 처리이고 API 호출은 외부 서비스 통신이므로 책임을 분리했습니다. 이 구조는 각 단계의 오류를 구분하고 기능을 독립적으로 수정하기 쉽습니다.

### 2-2. 프롬프트 구성과 출력 포맷팅을 어떻게 분리했는가?

`prompts.py`가 모델 입력과 지침을 구성하고, `main.py`와 `validator.py`가 응답을 추출·검증·출력합니다. 프롬프트 문구와 결과 처리 규칙을 각각 수정하기 쉽도록 했습니다.

### 2-3. API 파라미터를 CLI 옵션으로 둔 이유는?

모델, temperature, 최대 출력 토큰 수를 코드 변경 없이 실행마다 조정할 수 있습니다. 용도에 맞게 결과의 변동성이나 길이를 조절할 수 있습니다.

### 2-4. 오류 처리를 어떻게 구현했고 왜 그렇게 했는가?

Git 명령 실패, API 키 누락, API 요청 실패 등을 `RuntimeError`로 전달하고 최상위 실행부에서 오류 메시지를 출력합니다. 사용자에게 실패 원인을 알리고 정상 결과처럼 진행되는 것을 막기 위한 구조입니다. 개선 시 오류 유형별 안내와 비정상 종료 코드를 추가할 수 있습니다.

## 항목 3. AI 파라미터와 프롬프트 이해

### 3-1. temperature를 높이거나 낮추면 어떻게 달라지는가?

낮은 값은 표현의 변동성이 적고 더 일관된 결과를 기대하게 합니다. 높은 값은 다양한 표현이 나올 가능성을 높입니다. 간결하고 안정적인 커밋 메시지에는 낮은 값이 적합하지만, 정확성을 보장하는 설정은 아닙니다.

### 3-2. max_tokens의 영향과 설정 근거는?

생성 가능한 최대 응답 길이를 제한합니다. 너무 낮으면 설명이 잘릴 수 있고 너무 높으면 필요 이상으로 긴 응답을 만들 수 있습니다. 기본값은 500이며 CLI 옵션으로 조절할 수 있습니다. 커밋과 PR에 필요한 길이에 맞춰 조정합니다.

### 3-3. 목적에 맞는 결과를 위해 프롬프트에 무엇을 넣었는가?

Git status와 diff를 입력하고, 실제 변경 내용만 설명할 것, 근거 없이 추측하지 말 것, 제목 길이와 형식, PR 섹션 및 불릿 규칙을 지정했습니다. PR에는 현재 브랜치 정보도 포함합니다.

### 3-4. 재생성과 후처리 중 무엇을 선택했고 왜인가?

현재 구현은 재생성 대신 코드 후처리 검증을 합니다. 추가 API 요청의 비용과 지연 없이 출력 형식을 확인할 수 있기 때문입니다. 검증 실패 시 경고를 보여 주며, 필요하다면 추후 제한된 횟수의 재시도 정책을 추가할 수 있습니다.

## 항목 4. 검토, 보안, 향후 개선 판단

### 4-1. AI가 쓴 내용을 바로 사용하면 안 되는 이유는?

AI가 diff를 잘못 해석하거나 변경 내용을 과장하고, 실제로 하지 않은 테스트를 제안할 수 있습니다. 결과는 초안이므로 실제 변경과 대조해 사람이 확인해야 합니다.

### 4-2. diff의 민감정보 유출을 어떻게 막는가?

`--safe-mode`는 API 키 형태, Bearer 토큰, 이메일 주소를 정규식으로 마스킹하고 diff 줄 수도 제한합니다. 정규식 기반 탐지는 모든 비밀정보를 찾지 못하므로 완전한 보호가 아닙니다. 전송 전에 diff를 확인하는 것이 필요합니다.

### 4-3. 실제 팀에 적용한다면 무엇을 먼저 개선하고 왜인가?

먼저 민감정보 탐지와 API로 전송되는 diff 범위를 개선하겠습니다. 소스 코드와 설정 파일에 비밀정보가 들어갈 수 있고, 현재 마스킹은 일부 패턴만 처리하기 때문입니다. 이어서 staged 변경과 새 파일까지 정확히 수집하고, 오류 종료 코드·재시도 정책·자동화 테스트를 보강하겠습니다.

## 현재 구현의 한계

- `git diff`는 기본적으로 unstaged 변경을 출력합니다. staged 변경만 있거나 새 파일인 경우 변경 내용이 diff에 포함되지 않을 수 있습니다.
- Safe Mode는 줄 수를 제한합니다. `limit_diff()`에 `max_files` 인자가 있지만 현재 파일 수 제한에는 사용하지 않습니다.
- PR과 커밋의 일부 형식 규칙은 프롬프트로 요청할 뿐, 코드가 전부 강제하지는 않습니다.
- API 오류를 출력해도 현재는 프로세스가 0이 아닌 종료 코드를 반환하지 않을 수 있습니다.
- temperature 조정은 결과의 경향에 영향을 주지만, 같은 입력에서 동일한 차이를 항상 재현하지는 않습니다.

## 마무리 답변 예시

> 이 프로젝트는 Git 변경 수집, 프롬프트 구성, Gemini API 호출, 결과 검증을 역할별 모듈로 나눈 CLI 도구입니다. 생성 결과는 커밋이나 PR에 바로 적용하지 않고 검토할 초안으로 보여 줍니다. Safe Mode로 일부 민감정보를 가리지만 완전한 탐지는 아니므로, 팀에 적용하기 전에는 민감정보 보호와 staged·새 파일을 포함하는 변경 수집을 우선 개선하겠습니다.
